## 背景

引入工具循环前，本地 AI direct 模式下的面板对话是一次性请求：客户端把条目塞进
`localAIContext`，主进程 `streamText` 直接出答案，模型没有取数工具。

当时的限制：

- 「全部」视图：只能看到渲染器 store 里的条目，且本地库每源只保留最新 20 条
  （`packages/internal/database/src/services/entry.ts` 的 `ENTRIES_KEPT_PER_SOURCE`），
  不是账户的未读集合。
- 预算只有 20 条带正文（30000 字符），其余最多 200 条只剩标题。
- 模型无法追问、无法自己取更多，也无法访问用户已配置的 MCP 服务。

账户级全量未读能力其实已经存在，但只对外部智能体开放
（`apps/desktop/layer/main/src/local-agent-reading/`，MCP 端点 `127.0.0.1:41610`）。

## 目标

让面板里的 AI 自己取数据：主进程使用 AI SDK 工具循环，提供 Folo 只读工具和用户配置的 MCP
工具。MCP 只读工具可直接执行，其余工具必须逐次人工审批。用户不再需要在提示词里手工搬运条目。

## 用户故事

1. 在「全部」视图问「把今天的未读整理成一个清单」，AI 自己找到账户里今天的未读并逐条给出处。
2. 点开某个订阅源问「这个源还有什么没读」，AI 只在这个源里枚举，并给出未读条数。
3. 已经配置了 Notion/Linear 之类 MCP 服务时，AI 能读那里的内容并在同一段回答里综合。

## 范围

**做**：工具循环（多次往返）、Folo 只读工具、MCP 工具与逐次审批 UI、工具卡片渲染、
模型不支持工具时的当前请求降级、预算与截断、失败与取消。

**不做**：Folo 自身的写操作（标已读、收藏等）、预置或永久批准 MCP 写操作、pi 集成、
服务端（Folo 官方 AI）路径的改动。

## 验收标准

1. 面板 AI 在「全部」与单个订阅源两种路由下，都能通过工具拿到未读条目，且回答里引用的条数
   与工具返回的 `counts` 一致；单源提问不会返回其他源的条目。
2. 读取前后应用的未读计数与未读 ID 集合不变（复用 local-agent-reading 的只读断言口径）。
3. 工具调用在消息里可见（通用工具卡片），失败时显示错误而不是静默丢弃。
4. 首次明确拒绝工具且尚未输出内容或工具调用时，当前请求无工具重跑一次；同一端点和模型在
   本次应用运行内不再试探。已经输出内容或执行工具后不重跑，避免重复操作；其他错误正常显示。
5. 单次对话的工具步数与 token 有硬上限；超限、超时、用户中断都能干净结束。
6. 类型检查、lint、单测通过；`pnpm run typecheck && pnpm run lint && pnpm run test` 全绿。
7. 首发、重新生成和审批续跑保留同一条消息的有效 scene；显式来源切换保留原日期边界。
8. 预摘要不以较短正文覆盖更完整的已附内容，最终 prompt 区分正文与摘要；已有足够正文时不重复抓取。

## 风险

- 端点能力差异（deepseek 系对 `tool_choice` / 并行调用支持不一），必须有探测与降级。
- 工具执行依赖 renderer 桥（主进程 → 渲染器），无窗口、未登录、store 未 hydrate 时要给明确错误。
- MCP 服务返回体量不可控，不截断会撑爆 prompt。
- 现有 `ToolWithState` 状态联合缺少审批态，类型层面要一次性理清，避免后续写操作阶段返工。
